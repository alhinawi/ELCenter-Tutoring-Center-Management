Each phase is a real pull request with tested server persistence and usable screens. A phase is not complete merely because its navigation label exists.

The original request includes extensive details within each phase. The implementation should preserve that scope rather than treating this table as permission to omit it. External payment processing, outbound notifications, Google authentication, object storage and scheduled infrastructure require separately configured provider capabilities. Free operation and no purchases remain binding constraints. Provider-dependent features must never claim success without a provider delivery result.

## Remaining depth within earlier phases

The core workflows above are not a claim that every detailed requirement is already delivered. Later increments implement course prerequisite enforcement, atomic package enrollment/draft billing and independently approved backoffice attendance corrections. Before final commercial-readiness sign-off, finish remaining teacher contract depth, enhanced academic reporting, remaining profile detail, full accessibility audits and print-specific layouts. Identity-bound self-service portals and scoped document uploads are already implemented. External guardian delivery needs configured channels and must not be described as sent merely because an in-app alert was saved.

## Finance delivery notes

Phase 4 adds persisted invoice issue, partial receipt/refund, draft installment plans, approved expenses, supplier payables and partial settlements, balanced immutable double-entry journals with reversals, branch scopes, closed-period guards, cutoff-aware balance sheets, income/trial balance and cash/bank movement reports, cleared-line reconciliation, and six teacher compensation formulas with immutable calculation snapshots and separate preparer/approver/payer. Print views provide invoices/receipts and teacher payslips. These are operational records, not a payment gateway or a claim of statutory accounting compliance.

Remaining detailed finance scope before final sign-off: automatic payroll loan deductions, loan corrections/write-offs, configurable revenue classifications and recurring subscriptions, richer cost-center dimensions beyond branches, independent accountant review, asynchronous large-ledger exports. Cash-flow output is a cash/bank movement breakdown by source, not a statutory operating/investing/financing cash-flow statement. Reconciliation matches selected statement-cleared ledger lines once; it does not connect to a bank or import bank statements. Invoice and receipt print views are not electronic tax invoices.

## People and admissions delivery notes

Phase 5 adds branch-scoped employee profiles, departments, contracts with explicit ISO workdays and overtime rates, staff attendance, shift overlap/leave guards, independent leave decisions, reviews/history, recruitment stages and one-time offer-to-hire. Employee payroll uses a full-month contract, complete recorded attendance, approved leave, explicit workdays, overtime, bonus/deduction reasons and an immutable calculation snapshot. Approval accrues wages to payroll payable, then a separate payer records settlement. Partial-month or ambiguous contracts are held for review, not guessed.

Admissions includes campaign attribution, assigned advisers, lead follow-ups and interaction logs, one-time student conversion, acquisition counts, branch coupons with issue-time limits, visits/appointments and ordered check-in/out. Personal inboxes, notification preferences, stored templates and branch announcements have stored/read/blocked logs. External email, SMS and WhatsApp remain blocked until a provider is configured; no messages are claimed sent.

Remaining detailed scope includes automatic loan payroll deductions and loan corrections/write-offs, configurable paid-leave entitlements, referral-reward accounting, seasonal package validity, richer automated reception queues, external delivery providers and the remaining configurable automation rules. Scoped contract documents, operational package enrollment and a bounded subset of in-app reminders are implemented by later increments. Earlier phase details remain binding until the final verification pass.

## Portals and LMS delivery notes

Phase 6 introduces explicit, administrator-managed links between a login and one student, guardian or teacher profile. Self-linking and email-based identity inference are not allowed. These system roles cannot use generic backoffice APIs. Each portal and class operation checks the linked identity, organization, branch and enrollment/teacher assignment on the server. Unlinking revokes existing sessions.

Students and guardians can view permitted profiles, schedules, attendance, finalized results, issued invoices and recorded receipts/refunds. Guardians can switch between explicitly related children. Family absence, meeting and contact requests are stored for an independent administrator response, which enters the requester's own inbox. Invoice print/PDF uses the saved financial record, not a payment claim.

Teachers have assigned-class rosters with class-only performance aggregates, personal schedules and attendance recording, exam/question authoring, final grade review, lesson and assignment management, moderated class discussions and linked-family announcements. Leave requests require HR to bind the same active employee, teacher and login; the normal independent HR decision workflow applies. Salary statements show only approved/paid teacher payroll snapshots, not another teacher's figures or draft payroll.

The LMS stores published article/video/live/material links, one-time homework submissions, bounded grades/feedback, completed lessons and class discussions. Learners never receive question answer keys. Quizzes submit once, automatically grade supported question types and hold essays for teacher review. Submitted coursework is protected by database locks; published exams keep the earlier grading-rule locks. Demo lessons/materials are explicitly flagged. No shared privileged demo login is added.

Scoped encrypted PDF/file upload and support tickets are implemented in phase 7. Payment gateway, conference-provider creation and external delivery remain provider-dependent open work. External HTTPS links are labeled resources, not hosted video or access-controlled third-party content. Protected application metadata does not make a third-party URL private. Completion is based on published lesson checks, not proof of video watch time or an accredited certificate. Quiz attempts currently have a start time and manual close, not timed/proctored exam sessions. Broader keyboard/focus, recovery and load testing remain part of the final security pass.

## Resource and service delivery notes

Phase 7 persists inventory catalogs/suppliers, nonnegative immutable movements, independently received purchase orders, independent branch stock and asset transfers, invoice-bound physical dispatch/one-time stock returns, assigned assets/maintenance, book/copy catalogs, first-in reservations, unique active loans and saved late penalties. Support has scoped requesters, internal notes, independent staff assignment, resolution times, immutable satisfaction and encrypted attachments. Documents use authenticated permission checks, AES-GCM encrypted bytes, immutable versions, search, expiry filters/in-view warnings and download audit. Teachers can share class attachments; families can read shared documents and borrowing history. Reports have branch/course/teacher/date filters, operational data, Excel/CSV and landscape PDF/print.

Free document storage is deliberately small: 128 KiB per PDF/PNG/JPEG version, 20 retained versions per document, 1000 document records per organization. Signature checks are not malware scanning. Downloaded files remain untrusted. A dedicated, stable DOCUMENT_ENCRYPTION_KEY must be stored securely by the deployment operator and included in protected recovery procedures. Missing/wrong keys fail closed. D1 storage and daily reads remain shared with other applications. This is not unlimited object storage.

Later phase-8 work adds bounded in-app expiry reminders and private scheduled capacity/session/collection digests. These are not a full scheduled reporting/export service, and the optional Worker still needs separate deployment. Remaining detailed scope is still binding. Inventory valuation is standard catalog cost, not FIFO or a perpetual inventory ledger. Purchase receipt changes stock but does not automatically create/settle a supplier payable; finance retains its separate approval and settlement workflow. Physical dispatch does not charge a payment gateway; returns never silently refund an invoice. Library penalties are records, not collected money. Cross-center analytics explicitly label current counts versus historical cohort retention, room booked minutes versus utilization capacity, and lesson progress versus certified completion. Final release must finish or clearly hold those unmet detailed requirements rather than claim commercial completeness.

## Attendance correction increment

Initial backoffice attendance remains an atomic bulk entry. Once recorded, status/time/notes changes need a persisted correction and another user with attendance:approve permission. The request snapshots the attendance revision; database guards reject direct changes, self-review, repeat decisions and approval after a conflicting revision or session cancellation. Approval changes attendance, revision and absence-alert state atomically, with audit history. The current request form edits status/notes and preserves arrival/departure; the validated API supports time corrections. Review queues show the latest 100 requests in current branch scope. Later increments add identity-scoped teacher/family status-correction requests and request history. Configurable approval routing and portal time corrections remain open. Approval does not send external messages or alter payroll snapshots.

## Course prerequisite increment

Course details configure up to 20 active direct prerequisites. Cycles, self-references and duplicate links are rejected; database guards enforce completed enrollment in every prerequisite before new active/waiting enrollment or reactivation/transfer. Existing enrollments are not retroactively removed when requirements change. Completion means a staff-recorded completed enrollment, not a passed exam or certificate. Archived prerequisite links remain visible until explicitly removed. Branch users cannot inspect prerequisite course details outside their scope. Course duplication does not copy prerequisite rules. The following package increment adds fixed-price bundle enrollment and draft billing; recurring subscriptions remain open; a later increment adds optional package enrollment windows.

## Course package increment

Fixed-price, currency-snapshotted packages contain 2–10 active courses assigned to one branch. Enrollment selects one active group per course and creates all enrollments plus one draft invoice in one transaction. Group capacity, prerequisites and branch/student eligibility apply; a failure rolls back everything. Package terms and order snapshots are immutable; archive/restore controls new use. Up to 100 package definitions per organization. Invoice issue, receipts/refunds and enrollment withdrawal remain explicit independent workflows. Voiding a draft invoice does not silently withdraw enrolled students, and a student cannot buy the same package definition twice. This is an operational bundle, not a recurring subscription or payment gateway. Tax rules and referral rewards remain open; optional package enrollment windows are added below.

## Complete-journal ledger pagination increment

The ledger now uses descending date/created-time/id keyset cursors with 1–25 complete journals per page. All journal lines stay together; the old 2,000-line silent truncation is removed. Cursors are bound to current organization, branch scope and date range, and current permissions still apply on every request. Pages are live reads, not a frozen accounting snapshot: newly posted or backdated entries may require refresh, and previous-page navigation repeats the earlier keyset query. The visible-page CSV includes all lines on that page, has a UTF-8 BOM and neutralizes spreadsheet formula prefixes. Its button requires finance export permission, but any finance viewer can already read those records. This browser download does not yet create a server export audit event. Later increments add audited one-query single-account and bounded all-account exports with running balances. Larger asynchronous jobs remain open. Migration 0025 adds only two journal cursor indexes; no production migration is included here.

## Low-attendance family reminder increment

A default-off rule stores in-app family attendance notices below a configurable 1–100% threshold with 7–90 organization-calendar-day lookback and 1–50 minimum recorded sessions. The default is below 75%, 30 days and five sessions. Counts combine ended, noncancelled, nondemo sessions from current active enrollments/groups in the student's current branch. Present, late and left early count as attended; excused and unrecorded sessions are excluded. Session start must be inside the calendar window and its end must be no later than the run. This is recorded attendance, not proof of participation or historical cohort retention.

Current linked student/guardian identity, active membership/profile, role, branch, preferences, settings and identical counts/name are rechecked before insertion. Dedupe is per student/recipient/organization-local month, before the 100-recipient cap. A changed threshold does not resend within that month, and an old delivered notice is not recalled after correction or unlinking. Existing optional scheduler deployment and round-robin capacity limits still apply. No external delivery, automatic penalties or payroll changes.

## Invoice print-identity increment

Demo cleanup removes only snapshots belonging to explicitly demo invoices. ## Automatic invoice numbering increment

A default-off organization-wide invoice sequence supports an explicit uppercase/digit prefix with slash, underscore or hyphen and a monotonically increasing integer. Leaving a new invoice number blank uses the sequence; manual numbers remain available. Counter advance and draft/item/audit creation share a transaction, so validation/collision failure consumes no number. Concurrent create tests get distinct numbers. Settings compare the saved next counter before editing, and the database rejects backwards counters or deletion. Changing the prefix never resets the counter. Explicit forward jumps are allowed and auditable; this is not a statutory gapless sequence.

The UI preview is unreserved. A manual collision rejects a create rather than silently skipping, so headquarters must choose a safe prefix or explicitly move forward. The maximum counter is 999,999,999, which is treated as exhausted for automatic creation. Existing/issued invoices, package-generated numbers and receipt IDs are unchanged. No annual/branch reset or receipt numbering is included. Production concurrency/load validation remains a separate gate beyond local tests.

The dialog root remains focusable when no controls are available.

Browser checks cover each modal family, forward/backward wrapping, repeated Tab containment, Escape/restoration, global-search autofocus, background-focus redirection, Arabic mobile and nested support/document upload. This is bounded keyboard handling, not a WCAG conformance statement or a finished screen-reader, contrast, mobile-menu, calendar or assistive-technology audit. Unsaved-change prompts are not added; Escape follows each dialog's existing close behavior.

## Private profile-photo increment

Students, teachers and employees have one encrypted current photo. Administration uploads and removes photos under the profile's current branch and academic-edit or HR-edit permission; view uses the corresponding view permission. Linked students/guardians read only their own family's student photo, linked teachers only their own teacher photo, and neither can upload through self-service. Every read checks the current identity, role and record scope. Responses use private no-store and no shareable media URL. Views, replacements and removals are audited without photo bytes.

To fit bounded free storage, the browser accepts PNG/JPEG up to 8 MiB and resizes to at most 384 pixels, flattens transparency to white and re-encodes JPEG without original metadata, reducing quality until it fits 32 KiB or rejecting it. The API accepts PNG/JPEG at most 32 KiB and checks signature/header dimensions up to 512 pixels. These are not a full image decoder or malware scanner. A separate table stores AES-GCM ciphertext with per-write random IV and organization/entity/record/version-bound authenticated data, using the existing document-encryption secret. Replacement has no version history. There is a database-enforced 100-photo organization cap across all three profile types; replacement works at the cap. Record deletion removes its photo, including normal demo cleanup. No third-party media service, public bucket or biometric matching is added. Production key backup, migration application and shared-D1 storage/load checks remain operator gates.

## Optional receipt numbering increment

Headquarters finance managers can enable a separate, default-off organization-wide receipt sequence. A database trigger reserves a number only for a new real receipt, in the same transaction as its payment/journal/audit. Refunds, explicitly demo receipts and old records never consume a number. Original receipt UUIDs remain visible and immutable; assigned display numbers remain immutable across setting changes or refunds. Both backoffice and linked-family invoice views and print expose the saved number, with legacy IDs as fallback. Exact idempotent payment replays return the original number; changing amount/date/method/reference with the same key rejects the request.

Settings reject backwards counters and stale next-counter edits. Prefix changes do not reset the counter; explicit forward jumps remain possible. Unique-number collisions and the maximum counter (999,999,999, treated as exhausted) roll back the complete receipt and journal instead of consuming a number or silently skipping. Disable numbering to resume legacy-ID receipts after exhaustion. There is no manual receipt-number override, annual/branch reset, numbering of refunds, retroactive backfill, statutory gapless guarantee or tax certification. This labels recorded receipts only and never collects or sends real funds. Production concurrency and shared D1 checks remain operator gates. Migration 0030 adds two isolated tables/triggers and does not change existing payment rows.

## Audited single-account statement export increment

Finance viewers with explicit export permission can download one account's complete statement for the applied inclusive date range and current membership branch scope. A single financial SQL query captures posted movements, opening balance before the range, deterministic date/created-time/journal/line order and debit-minus-credit running balances. Credit balances are negative; reversals remain their own posted movements. Empty periods retain their opening balance. The query includes all prior posted history needed for opening, not just visible ledger pages. Later/backdated postings require a new export. There is no persistent, signed or reproducible statement archive.

The export records its account, filters, branch, generation time, row count and balance summary in the audit log before returning data. It requires both view and export permission on every request. The 5,000-period-movement cap rejects the whole request with a narrower-date instruction, never emits a partial statement, and does not falsely audit success. CSV includes account/currency/scope/basis metadata, full movement IDs and totals, a UTF-8 BOM, escaping for delimiters and formula-looking text, and actual numeric negative balances. It is a local browser download, not external delivery. This is a single-account statement, not an asynchronous large-export service; the following increment adds a bounded all-account export. No new migration or remote production operation is required; production load and shared-D1 quota checks remain open.

## Complete scoped ledger CSV increment

A separate all-account export includes every posted journal and every line in the applied inclusive dates and current membership branch scope, independent of interactive page cursors. One financial SQL query captures account opening balances before the range, all period movements with deterministic journal-grouped order, per-account debit-minus-credit running balances, and account closing/debit/credit summaries. Accounts with posted history through the end date are included even without current movements. New/backdated entries require a fresh export; generation time does not establish a retained or signed accounting archive.

Both finance view and export permission are required. The server verifies overall debit/credit and opening/closing balance before preparing the result, and audits the dates, scope, generation time, movement/account counts and totals before returning it. CSV includes full IDs, account summaries, currency/scope/basis metadata, formula-safe text, BOM and numeric signed balances. A hard 5,000-statement-row limit counts movement rows plus one row per history-only account. Larger requests reject entirely with instructions to narrow dates or use one-account statements. No partial journal or ledger is returned, and a rejected request is not audited as a successful export. Tests cover empty ledgers, historical-only balances, reversals, 26 journals across interactive-page boundaries, exact cap, cap rejection, branch changes, revoked permissions and organization isolation. This closes the bounded all-account export gap, not large asynchronous exports, live D1/load validation or statutory certification. No migration or production change is included.

## Strict calendar-date validation hardening

Academic birth dates, course registration windows, group start/end dates and holiday creation now reject impossible calendar dates such as February 30, non-leap February 29 and April 31. JavaScript parsing previously normalized some of these; the holiday API checked format only. A shared canonical YYYY-MM-DD validator uses strict Gregorian calendar parsing without timezone conversion. Existing strict finance/report/ledger/package/custom-field validation now shares that same implementation. Academic create, edit and bulk import reject before persistence or successful audit records, and course duplication validates the source before making another copy. Valid leap days and optional blank dates retain their existing semantics.

This is API-boundary protection, not a database cleanup or direct-SQL constraint. Historical invalid values, if any, are not rewritten or silently normalized. Staff must explicitly correct such a source before duplicating it. No migration or remote data change is included. Regression tests cover leap-year century rules from 1896 through 2104 in three timezones, canonical formatting, student create/edit/mixed imports, course/group writes, duplication, holidays and existing strict financial exports. This does not settle the independent course-capacity or registration-policy decisions.

## Team-directory and role-audit hardening

The team directory now applies the authenticated membership's current branch as well as organization scope, including custom roles that have users:view.
